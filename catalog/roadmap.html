Verification gate & standing invariants
2026-08-24

Run from catalog/ and report each command separately. A green SPA run does not stand in for backend tests.

npm run typecheck && npm run test:backend && npm run test:spa && npm run build
Existence invariant. The catalog tracks provider-declared model existence — not model runtime availability, health, latency, or whether inference currently succeeds. A model is in the catalog because a provider published it in a roster this catalog fetched successfully. Nothing else adds or removes it.
Conflict definition. A conflict exists only when two or more sources that are each entitled to speak about this offering declare materially different values for the same field, and no ranking rule can settle it. A model being new, a model being removed, a value changing between runs, and a fetch failing are not conflicts — each has its own path.
Work-once invariant. A model is measured once, when it first appears. An existing model is never re-probed, re-scored, or re-enriched because a sibling changed, a sync ran, or a new model arrived. Re-derivation from already-stored source data is permitted and is not re-testing.

CSS-module types are index signatures. src/vite-env.d.ts:4 declares { readonly [key: string]: string }, so styles.anythingAtAll type-checks and renders class="undefined". The compiler cannot catch this and never will; npm run check:css-modules does, and runs inside typecheck. Closed by Q3 on 2026-08-25.

Do not redirect gate output into catalog/. The root .gitignore hides *.log, so redirected output never reaches a diff and simply accumulates. Read the output, or send it to the session scratchpad.

3 · The conflicts problem — root cause

The reported symptom — a new model, fully processed, appearing under Conflicts — is real, and it is produced by two independent defects. Neither of them reads prior catalog state, so "the model is new" is not an input to conflict creation anywhere in the code. Nothing needs to learn that new models are exempt; the comparison itself is wrong.

Defect A — a mode variant is pooled as if it were a rival seller.

The unanimous(list) test that runs first, and the first-party branch that runs last, both count the thinking-mode listing as an independent seller. The code's own comment at lines 371-372 states this is the bug it fixed; the fix was scoped to one branch.

Structured output being true in thinking mode and false in the base mode is not a disagreement between sources. It is one source describing two modes of one product.

Correction — 2026-08-24, after K1 landed. The evidence table above misreads its own citation. The true side was attributed to nano-gpt/longcat-2.0:thinking only because the sides list keeps one entry per distinct value and the mode listing happened to be the first declaration carrying true. Read back from models.dev/api.json on 2026-08-24, the base listings are: nano-gpt/longcat-2.0 → true, openrouter/meituan/longcat-2.0 → false, kilo/meituan/longcat-2.0 → false; the serving seller opencode-go and the vendor storefront longcat publish no value. So this dispute is genuine between base sellers and a conflict row is the correct outcome — excluding the mode variant does not remove the true side, it only re-labels it. Defect A is still real and still fixed: it is proven by the two unit tests on settle(), and by the one live mode-variant conflict K3 dropped. What cleared this row from the Conflicts surface is K2 plus the measurement that answered the field — structured = true, 300 samples, so the dispute now carries a recorded verdict and is resolved, not open.

Defect B — a settled conflict still renders as a conflict.

server/read-model.ts:449 selects every row of model_conflicts with no status predicate and hands the whole list to the client. Three surfaces then treat presence in that list as "conflicted": the summary count at read-model.ts:784, the panel section at EvidencePanel.tsx:141, and the per-field badge at FactState.tsx:37. Fifteen of the sixteen live conflicts are already status='resolved' with a recorded resolved_to — a person's verdict — and they still show as unsettled disputes.

What must not change. Real conflict detection stays. The open rows include genuine two-sided disagreements between entitled sources. Neither fix filters the UI to hide a conflict: both stop a false conflict from being created or mis-rendered at the point where the judgement is made.
4 · Model lifecycle — the required contract

New model — full processing, once.

Provider roster→Not known locally→Insert→Probe + enrich→Score + evidence→100% complete→Persist→green notification

Existing model — nothing happens.

Provider roster→Known locally→Keep stored data·no probe·no re-score·no re-validation·no notification

Removed model — absent from a successful roster fetch means gone, immediately.

Roster fetch succeeds→Model absent→status = retired→excluded from every default read→red notification

The row and its events are preserved. retired is the removal: it takes the model out of /v1/models, out of liveModels, and out of every published view. That satisfies both the requirement and the never-physically-delete rule in catalog/CLAUDE.md and db/schema.sql. No waiting period, no re-test, and no question about whether the model still answers requests — that question is outside the catalog's scope.

Fetch failure — the catalog does not move.

Fetch fails→record the run→catalog untouched·no miss counted·no retirement→yellow notification

Real conflict — two entitled sources, materially different values, no ranking rule settles it. Recorded against the offering, surfaced while open, cleared when a reviewed fact settles it.

Guards that stay. A roster that returns 200 OK but truncated is a different failure from a fetch that errors. maxRemovalRatio: 0.3 and maxRemovalCount: 5 (sync/engine.ts:108-111) quarantine a run that would drop an implausible share of a provider's catalog. Those layers are unaffected by the change to retireAfterMisses and must not be removed alongside it.
5 · Notifications — final behaviour

No fourth category. No fix button, no retry action, no recovery workflow, no per-notification state beyond read_at. A notification arrives unread; opening the panel marks the shown notifications read. That is the entire model, and it is what the code already does.

The number 500 — answered, not guessed. There are two unrelated 500s and neither is a notification state machine:

  • server/changes.ts:57-58 — DEFAULT_CHANGES_LIMIT and MAX_CHANGES_LIMIT, the page-size ceiling on the public GET /v1/changes feed. Unrelated to notifications.
  • server/model-notifications.ts:155 — the ceiling on GET /v1/notifications?limit=, so a caller cannot ask the service to serialize the whole table. It is duplicated inline at server/app.ts:197 instead of being imported, which is the only real problem with it. Tracked as N3.

Both are ordinary boundary limits and both stay. The comment at model-notifications.ts:117 that mentions "more than 500" is explaining that reconciliation is deliberately not bounded by them; it is correct as written.

The cap that actually hides content was 5, not 500. NotificationCenter.tsx capped the panel at MAX_VISIBLE_NOTIFICATIONS = 5 while the badge read summary.unread, which counts every row — a bell reading 135 over a panel showing 5, with no pagination and an orphaned .viewAll rule in the stylesheet. Closed by N2 on 2026-08-25: the render cap and the dead rule are gone, the client asks for the page maximum instead of the default, and the panel states the shortfall if a catalog ever outgrows one page. The ceiling that remains is the request limit, which is the boundary that should own it.
