### M5.1 provider-policy corrections (2026-08-13, owner-decided)

Two provider billing/publish policies were corrected after live measurement. Both
are keyed on typed capability/policy, never a slug switch, and both were TDD'd
and verified end-to-end on a throwaway `verify.db` with two real enrich passes.

**Ollama Cloud — `free`, not `included`.** Ollama Cloud is free at point of use
and quota-limited (quota is OAuth-only and out of scope). models.dev publishes no
per-token cost for any of its models, so under the old `subscription` policy every
Ollama model resolved to `included`. A new `BillingModel` value `free_quota` now
resolves a missing price to `free` — with **no fabricated number**: the effective
price stays `null`, only the KIND says free, and `billingKind` carries
`provider_billing`/`declared_policy` provenance. This deliberately avoids the
laundering trap an earlier attempt hit: a derived `$0` written into the price
columns is re-read by the SECOND enrich pass as a first-party models.dev price.
`computeVO` now scores `billingKind === 'free'` as the cheapest even when no
per-token figure exists, and the cost population counts free as `0`. Regression
test: `enrich.test.ts` runs two passes and asserts free/declared_policy with no
`effectivePrice` fact. Files: `sync/enrich/resolvers.ts`, `sync/providers/index.ts`,
`sync/score/venom-score.ts`, `sync/score/pipeline.ts`.

**OpenCode Zen — free-only publish.** Zen is the owner-declared free tier
(distinct from the paid OpenCode Go), but its live roster mixes free and paid ids
and models.dev prices most of them (measured 2026-08-13: 7 zero-priced, 53
non-zero of 60). A free tier publishes only what it currently SERVES for free: a
model must be both `active` (in the latest roster) and proven free. A new
lifecycle status `excluded` (with an `exclusion_reason` of `paid` |
`not_proven_free` | `not_served`) is set by a pipeline step
(`sync/publish-policy.ts`, driven by an adapter's `publishPolicy: 'free_only'`)
that runs after the roster is stored and before enrich/score: a paid model is
withheld `paid`, a model whose price cannot be shown to be zero is withheld
`not_proven_free`, and a model the provider dropped from its roster (status
`missing`) is withheld `not_served` — deterministic, independent of retirement
timing, so the count is exactly the currently-served free set. Every downstream
reader already gates on `status IN ('active','missing')`, so an excluded row
leaves the published catalog — and its populations and calibration — by
construction, while the row itself survives (history is never deleted) and the
roster delta gate is never touched (exclusion is a publish decision, not an
absence). Idempotent on `exclusion_reason`, so a later sync re-asserts silently
and never re-enters a paid model. Files: `db/schema.sql`, `db/index.ts`,
`sync/engine.ts` (adapter type only), `sync/providers/index.ts`,
`sync/publish-policy.ts`, `sync/pipeline.ts`, `sync/run.ts` + `server/index.ts`
(snapshot queries).

### Three holes found while doing this work

- **The backend was never type-checked.** The root `tsconfig.json` includes only
  `src`, so nothing in `sync/`, `server/` or `db/` was ever checked, and Node
  strips types without checking them — so a type error was invisible at build
  time AND run time. That is how `IntrinsicFacts` came to be declared twice.
  Added `tsconfig.node.json` + `@types/node` + an `npm run typecheck` script; the
  first run exposed 31 real errors, one of them a lost edit of my own.
- **`task gate` does not cover `catalog/` at all.** Its tests are outside the one
  blocking gate, so catalog work can never be claimed as gate-verified. Use
  `npm test` + `npm run typecheck` inside `catalog/` and say which was run.
- **The SPA has no test infrastructure of any kind** — no `vitest`, no
  `@testing-library/react`, no `jsdom`, and zero test files under `src/`. This is
  a prerequisite of the SPA round, not part of it; see below.

Item 6 grew a seventh: the overlay's `rejected` decisions were invisible to every
consumer, the same class of defect as the hidden conflicts. They are now a third
identity state in the data model — `identity_rejections`, ingested from the
overlay with the M5.1 provenance contract, one row per candidate, and never
capable of becoming a resolved identity.

A fourth hole surfaced once the SPA round was live: `DashboardPage.tsx` read
`meta.identityDetail.rejectedCandidates` and `.withRejectedCandidates`
unguarded, so a `meta` payload from a server still running pre-`identityDetail`
code crashed the whole page instead of degrading. Fixed by treating a missing
`identityDetail` as unknown — rendered with the same `FactState` "missing" chip
the rest of the catalog uses for a fact nobody sent — never as a fabricated `0`.
The client's `CatalogMeta` type staying required is correct; the fix is in what
the component does when a runtime payload violates that promise, not in
widening the type.

A fifth hole, found in the browser: that fourth fix was right about the
principle and too narrow about the blast radius. `identityDetail` was one field
of nine that a pre-M5.1 service omits, and it was the only one guarded. Against
the live service — a process started before this contract, still serving the old
shape — `/provider/clinepass` rendered a **blank page**: `VOCell` read `.length`
off an absent `vo.notApplicableDimensions` and React unmounted the tree. All 116
models were missing all six of `identityState`, `rejectedCandidates`,
`conflicts`, `provenanceByField`, `vo.notApplicableDimensions` and
`vq.unratedReason`; `meta` was missing `identityDetail`, `conflictedModels` and
`conflictsByField`, and carried the superseded `identity` sub-shape
(`resolvedWithEvidence` / `resolvedWithoutEvidence`).

Fixed at the seam instead of per component: `normalizeModel` / `normalizeMeta`
in `client.ts` are now the one place wire data becomes an `ApiModel`, and the
snapshot path goes through them too — so the fallback view cannot decide
differently from the live one. Absent lists and records become `[]` / `{}`;
absent meta counters become `null` and render as the `FactState` "missing" chip,
never `0`. Two fabrications were removed on the way: the snapshot path had been
reading `identityState` off `vq_source_model_id`, a *benchmark* column, and had
been publishing `conflictedModels: 0` and `identityDetail: {0,0,0}` for a
snapshot that carries no such column.

The superseded `identity` sub-shape is deliberately **not** mapped forward. Its
`unresolved` counted every row without a canonical id, which the current
contract splits into `identityReview` + `unresolved`; reading it across would
republish an old number under a new name, which is worse than no number. The
whole sub-object is taken as one answer or not at all.

**Hole 2c — a stale fact outlived its resolver.** Found by auditing the one count
that moved after the live restart, rather than assuming drift was benign.
`clinepass/cline-pass/qwen3.8-max` reported `context` and `maxOutput` as gaps
while the same Evidence panel showed "Context window | 1000000 | openrouter"
below it. The value was `qwen/qwen3.8-max.top_provider.max_completion_tokens` —
*a different seller's* cap, which `resolver-v2` deliberately stopped inheriting.
So the drop was correct; the leftover provenance row was not.

Root cause: `enrich()` upserted every fact it produced and **deleted nothing**.
A field that stopped resolving wrote nothing and left the previous run's row in
place, so the pass contradicted its own docstring — "re-running it reproduces the
same result and never accumulates drift". Conditional writes (`effectivePrice`,
`referencePrice`) and `model_conflicts` had the identical hole: a disagreement
the sources no longer contained kept being reported as open.

Fixed by making every run **rebuild** the derived state rather than add to it:
each row's facts and conflicts are read back after its writes and anything the
run did not prove is dropped, inside the existing transaction, counted in a new
`EnrichSummary.retired` so a vanishing fact is never silent. Deliberately **not**
a delete-then-insert — `model_conflicts.status` and `resolved_to` are a person's
verdict, and re-detecting a conflict is not grounds for discarding it; a test
pins that. Scoped per row, so one model losing a fact cannot take a neighbour's
provenance with it; a test pins that too.

Two things this deliberately does not do. It does not mask the contradiction in
the client — the SPA renders what the API sends, and papering over it there would
have hidden the defect instead of ending it. And the gate's `cost` is **not**
treated as forbidding `billingKind` or `referencePrice` provenance: `billingKind`
records *why* a price is unknown (`sourceRef: "no price published"`,
`evidence_state: declared_policy`) and `referencePrice` answers a different
question (the list price elsewhere). Only `effectivePrice` asserts "this is what
it costs here", which is the single claim a `cost` gap contradicts. An earlier
draft of the invariant test got that mapping wrong and passed anyway, because no
fixture row had a `cost` gap to exercise it — the test now asserts the fixture
produces one before checking anything.

Lesson worth keeping: all 37 SPA tests stayed green through this, because every
one of them built a complete `ApiModel` by hand. A fixture the test owns can
only prove the renderers agree with data they already agree with — it can never
catch a wire-contract gap. The two new files (`client.test.ts`,
`ProviderPage.test.tsx`) start from raw response bytes and go through
`fetchCatalog`, and they reproduce the blank page as a test failure.

**Hole 2d — the two orchestration paths did not consult the same evidence, and
2c's own fix turned that into active data loss.** Found by an independent
review before commit, returned **NO-GO** on exactly this: `sync/run.ts` (the
CLI) resolved facts in two passes — free shared sources, then each provider's
own detail endpoint for whatever was still open, then a second pass ranking
that answer first. `server/sync-runner.ts` (reached by `POST /v1/sync` and the
six-hour scheduler) ran only the first pass; it never asked a provider's own
detail endpoint at all. Against 2c's rebuild-on-every-run rule, that is not a
missing nice-to-have — it is active data loss: a fact ONLY detail could prove
looks, to a run that never asks it, identical to a fact the provider withdrew.
The service was running exactly that "never asks" run every six hours, so
every detail-sourced fact the CLI had ever established was on a six-hour clock
before the scheduler deleted it. The review named the concrete instance:
`deepseek-v4-flash:preview`'s `context`, sourced from `ollama.com/api/show`
because no index anywhere publishes it, would not have survived the next
scheduled tick.

The review named a second case in the same shape: a temporary failure of the
detail call for one row, within a single CLI run, must not read as "the
provider withdrew this fact" either — a failed call and a call never made are
the same absence of evidence, and `fetchOllamaDetail` already returns `null`
on any network error, so the two are indistinguishable at the call site by
design.

Fixed two ways, matching the two-part ask:

1. **One shared pipeline.** `sync/pipeline.ts` (`runSyncPipeline`) is now the
   only place that decides "sync rosters, enrich once, ask detail for what's
   open, enrich again, ingest rejections, score." `sync/run.ts` and
   `server/sync-runner.ts` both call it and nothing else — a step added there
   reaches both callers, and there is no second copy of the ordering to drift
   out of sync again. `SyncRunner`'s config gained `fetchJson`, `post` and
   `detailFetchers`, injectable for tests and defaulting to the real ones in
   production, mirroring the pattern already used elsewhere in this codebase.
2. **`enrich()` no longer treats silence from an optional source as a
   withdrawal.** A stale fact is pruned only when this run can show the source
   that produced it actually spoke: for a `provider_api`-sourced fact, that
   means `input.detail !== null` this run — the same value the resolvers
   already compute, so no new plumbing was needed to answer "was detail
   consulted, successfully, for this row, this run". `null` covers both "never
   asked" and "asked and failed" on purpose; either way, retiring the fact on
   the strength of it would repeat the exact mistake 2c's fix was written to
   end everywhere else. Kept-instead-of-retired facts are counted in a new
   `EnrichSummary.protectedStale`, for the same reason `retired` is counted:
   a disappearing (or a silently-kept) fact must be visible to someone reading
   the run's summary, not just correct in the database.

Verified, in order: `sync/enrich/enrich.test.ts` gained four tests proving a
detail-only fact survives a run that never consults detail, survives a failed
call for its own row while detail succeeds for a different row, and IS retired
once detail is asked again and genuinely stops reporting it — each confirmed
against a real mutation of the guard (removing the `input.detail === null`
check turns the first two red). `server/sync-runner.test.ts` is new: it runs
`SyncRunner.run()` — the exact method `POST /v1/sync` and the scheduler call —
network-free via the new injectable config, and shows a `provider_api`-sourced
fact now survives it, where before this fix it could not have been produced by
that method at all. A second test runs the CLI's own path
(`loadSpecs`/`loadBenchmarks` then `runSyncPipeline` directly) against
identical fake inputs on a separate database and asserts the two paths land on
byte-identical value and provenance for the same fact, plus matching scoring
totals — the concrete "CLI and service produce the same result" the review
asked for. Both new tests fail for the right reason when the pipeline's detail
pass is deleted by mutation, confirming they exercise the fix and not a
tautology. Then verified against the real live database: restarted the service
(third hash-verified backup — `pre-orchestration-fix-20260813-172307`,

## The frozen API contract the SPA round builds against

Read this before touching a component. Every field below is already served by
`GET /v1/models` and covered by tests.

### Per model (`ApiModel`)

| Field | Meaning the UI must preserve |
|---|---|
| `identityState` | `resolved` \| `identity_review` \| `unresolved`. Exclusive. The **service** may only assert these three. The client adds a fourth, `unknown`, that the service never sends and that means exactly "this response did not carry the field" — it is not a finding about a model, and it is never derived from `canonicalId`. Rendered as "identity not reported", distinct from `unresolved`'s "no upstream model matched". |
| `rejectedCandidates[]` | `{ candidate, verdict, why, evidence[], source, sourceRef, sourceUrl, evidenceState, resolverVersion, candidateMeta, reviewedAt, recordedAt }`. `verdict` is `candidate_rejected` or `no_candidate_exists` — a refusal and "nothing exists to refuse" are different findings. Empty array means nothing was tried, which is not the same as the field being absent. |
| `conflicts[]` | `{ field, sides[{value, by}], conflictType, status, resolvedTo, detectedAt }`. Every side is retained; there is no winner to render. |
| `missingFacts[]` | Named gaps from the completeness gate: `context`, `maxOutput`, `modalities`, `tools`, `reasoning`, `structured`, `cost`. |
| `catalogReady` | True only when `missingFacts` is empty. **VQ is deliberately not part of the gate.** |
| `vq.unratedReason` | `identity_unresolved` \| `identity_ambiguous` \| `no_published_benchmark` \| `calibration_group_excluded`, or null when scored. |
| `vq.display` / `vq.precision` | Pre-rendered at the precision the evidence supports. The client must never re-format or exceed it. |
| `vo.missingDimensions` | Dimensions nobody published — a real gap. |
| `vo.notApplicableDimensions` | Dimensions that **do not apply**, e.g. `cost` for a subscription model. Must NOT render like a gap. |
| `pricing.kind` | `free` \| `included` \| `per_token` \| `unknown`. `included` is an answer; `unknown` is not. |
| `pricing.reference*` | List price **elsewhere**. Never presentable as what the user pays. |

### Meta

```
identity:       { resolved, identityReview, unresolved }        // exclusive, sums to liveModels
identityDetail: { ambiguousOpen, withRejectedCandidates,        // subsets — NOT a partition
                  rejectedCandidates }
qualityScored, unrated                                          // a SEPARATE axis
conflictedModels, conflictsByField
catalogReady, needsVerification, operationalScored, liveModels
```

**`qualityScored` is not an identity bucket.** An earlier contract split
`identity` by whether a benchmark existed, which made that bucket numerically
equal to `qualityScored` and invited adding it to the identity states — a mistake
this plan's own first report made. "Resolved but unbenchmarked" is
`identity.resolved - qualityScored` (currently 6): derivable, deliberately not
stored inside the partition.

### Per-field provenance (`model_facts`)

Every displayed value has a row carrying `source`, `source_ref`, `source_url`,
`evidence_state`, `raw_value`, `resolver_version` and `probe_version`.
`evidence_state` is the field the UI needs and `source` cannot supply:
`first_party` | `pooled_third_party` | `index_confirmation` | `declared_policy` |
`measured`.

## The SPA round — six surfaces, one pass

The UI is an honest display of what the catalog already knows. It makes no
decisions, fills no gaps, and picks no winners.

1. **Complete / ready** — `catalogReady` shown as a state, not implied by a row
   looking full.
2. **Missing facts + reason** — the exact field, and why it is missing. A missing
   field must never render as though its value were known.
3. **Conflicts** — the disputed field, every side, the provider/source behind each
   side, and the conflict status.
4. **Provenance / evidence** — source, URL/reference, `evidence_state`,
   `resolver_version`, and `probe_version` when a probe produced the value.
5. **Identity review** — `identityState`, each rejected candidate, its reason, its
   evidence and source, and its candidate metadata.
6. **`notApplicable`** — visibly distinct from missing. Four states must be
   tellable apart at a glance: known value · not applicable · missing · unknown
   because sources conflict.

### Rules for the round

- Do not reintroduce raw or unqualified models into the main catalog table.
- Do not fabricate a value to make a row look complete.
- Do not silently choose a winner when the evidence conflicts.
- **A model can be operationally complete while its VQ is unrated.** An unrated VQ
  is never a reason to hide catalog-ready operational data — that is a statement
  about the world, not a hole in ours.
- Touch only what these six surfaces need. No unrelated UI rewrites.

### Prerequisite: SPA test infrastructure

Rule 8 of the round asks for focused SPA tests, and there is currently nothing to
write them with. Before the components change, add `vitest` +
`@testing-library/react` + `jsdom`, a `vitest.config.ts` that reuses the existing
Vite plugin config, and fold the run into `npm test` so a UI regression fails the
same command everything else does. Note the known jsdom gotcha already recorded
for this repo: jsdom has no `AnimationEvent`, so animation-event-driven behaviour
must be tested as pure decision logic rather than through the DOM.
