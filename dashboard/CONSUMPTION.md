# How this app consumes `@venom/design-system`

This is the dashboard-local record of the integration contract P2a-DS-005 locks in. It doesn't
replace `Design_System/SKILL.md` or `Design_System/validation/handoff-contract.md` — those remain
the authoritative package-side documents (07 §9/§10). This file records the choices *this app*
made and the rules it is held to.

## Pinned version

**`@venom/design-system@1.0.0`** — the version this app was built and reviewed against.

The dependency uses **mode 1** (workspace/local package dependency), per SKILL.md:

```json
"@venom/design-system": "file:../Design_System"
```

`file:` links don't carry a resolvable semver range the way a registry dependency would — npm's
lockfile just records `"resolved": "../Design_System", "link": true"` and always reads whatever is
currently checked in at that path. The real pin here is **governance, not lockfile immutability**:
the dashboard consumes only the package's public surface (see below), and any deliberate version bump must
update `PINNED_DS_VERSION` in
[`scripts/check-ds-adherence.mjs`](scripts/check-ds-adherence.mjs) *and* this file together — the
adherence check (wired into CI) fails closed if `Design_System/package.json`'s version ever drifts
from what's recorded here without that being a deliberate, reviewed change.

**Why mode 1, not mode 2 (handoff copy):** mode 1 keeps exactly one artifact (no copy to fall out of
sync), and this repo already builds `Design_System/` from source in the same checkout — mode 2's
deterministic-copy procedure exists for consumers who *don't* have that, per
`validation/handoff-contract.md`.

## The only legal import surface

Every import must resolve to one of `Design_System/package.json`'s own `exports` entries — nothing
else, ever:

| Subpath | What it is |
|---|---|
| `@venom/design-system` | Everything (index barrel) |
| `@venom/design-system/tokens` | Typed token values |
| `@venom/design-system/themes` | `THEMES`, `THEME_LABELS`, `DEFAULT_THEME`, `applyTheme` |
| `@venom/design-system/density` | `DENSITIES`, `DENSITY_LABELS`, `DEFAULT_DENSITY`, `applyDensity` |
| `@venom/design-system/icons` | Icon component + map |
| `@venom/design-system/primitives` | Presentational primitives (`Button`, `Table`, `ThemeSwitcher`, `DensityToggle`, …) |
| `@venom/design-system/domain` | Venom domain components (`AccountStatus`, `ProviderBadge`, …) |
| `@venom/design-system/tailwind` | `venomTailwindPreset` |
| `@venom/design-system/styles.css` | The one stylesheet |
| `@venom/design-system/themes/*.css`, `/assets/*`, `/package.json` | Supporting assets |

Reaching into anything else — most importantly **`@venom/design-system/dist/...`** directly, or any
other path the `exports` map doesn't list — is an internal/generated path and is banned.
`scripts/check-ds-adherence.mjs` derives this table from the package's own `exports` map at check
time (never hand-duplicated), so it can't silently go stale.

## Package ownership rule

The dashboard never vendors a copy of Design System component or token source and never hand-authors
a token→Tailwind mapping (that mapping is `venomTailwindPreset`, generated by the package itself —
P2a-DS-003). Package changes are allowed in the same repository when they pass the Design System's
own gates; the dashboard adherence check is deliberately about the consumption boundary. It fails
if any file under `dashboard/src/` shares a filename with a real
`Design_System/components/**` file or contains the package's generated-file header — both are
treated as a vendored copy rather than an import.

## Offline / no-CDN guarantee

Per `validation/handoff-contract.md`'s "Offline packaging" section: `Design_System` makes no
runtime network requests — webfonts fall back to the system stack, and the pinned Lucide icon set
is vendored locally. This app inherits that guarantee unchanged and adds no CDN script or stylesheet
tag of its own.

## Enforcement

`npm run check:ds-adherence` (CI-blocking, wired into the `dashboard` GitHub Actions job) fails
non-zero on any of: an internal/non-public import, a vendored component/token copy, or a version
drift from the pin recorded above. Package integrity is enforced by the Design System's own
validation, type, accessibility, and visual-regression gates.
